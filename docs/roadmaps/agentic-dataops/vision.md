# Vision — agentic-dataops

**Objective:** Ship v1 of Agentic DataOps (`adops`) — an Apache-2.0, uv-packaged Python CLI/library that scaffolds a user's Project (`adops init` / `adops init --demo`) whose YAML Pipelines (Sync via dlt for Verified Sources and PyAirbyte for Docker-free Community Sources, Transform via dbt, Reverse Sync to databases with Preview) are validated and compiled to Dagster, run against Postgres or DuckDB Warehouses across dev/stage/prod and Branch Environments, and are operated by the user's own Assistant through an MCP server and six skills with GitOps Promotion via GitHub Actions — so that a SQL-literate user with no Git or Docker knowledge can operate it.

**Success definition:** v1 is done when ALL hold: (1) installing the `adops` package yields a working `adops` CLI; `adops init` and `adops init --demo` scaffold a Project with pipelines/, a dbt project, Environment settings, docker-compose.yml, `.env.example`, the 6 SKILL.md skills and GitHub Actions workflows — no tool code copied into the Project. (2) In a demo Project, `docker compose up` starts the demo shop Postgres (Source), the Postgres Warehouse and the Dagster metadata Postgres (+ optional Grafana/OTel profile), and `adops run` executes a Pipeline that Syncs orders/customers (Full Refresh and Incremental Sync), Transforms them with dbt models + tests, and Reverse Syncs a result into a Postgres database — writing only in stage/prod and producing a Preview in dev/Branch Environments. (3) The same Pipelines run unchanged on a DuckDB Warehouse. (4) Invalid YAML, missing Secret Reference, unreachable Source/Warehouse, empty Source table and a Breaking Change each produce a clear sanitized error; a Breaking Change halts the affected Step and downstream Steps. (5) Branch Environments are per-branch schemas in the stage Warehouse that defer to stage, rebuild only changed Steps + dependents, re-sync only when a Sync Step changed, and are dropped on merge/close. (6) Secret References resolve only from env vars/.env and no output/log/span/MCP response contains a secret value, asserted by tests. (7) The MCP server exposes edit/validate/test-connection/run/Preview/read-logs only for dev and Branch Environments, refusing stage/prod in server code. (8) The six skills check prerequisites, perform Git operations themselves and narrate plainly. (9) Generated GitHub Actions run PR→Branch Environment+tests, merge→stage, release/approval→prod. (10) The tool repo's CI enforces 100% line+branch coverage on `adops` package code and runs the demo end-to-end in Docker on every PR; every Verified Source passes the E2E suite. (11) Playbooks exist for Environments/Promotion and single-VM production. (12) No LLM key or Wren container is needed anywhere.

**Domain shape:** business — The objective carries DataOps rules a data-engineering expert recognizes (Reverse Sync writes only in stage/prod, a Breaking Change halts downstream Steps, the Assistant acts only in dev/Branch Environments, Promotion via Git), with real seams between Pipeline authoring/compilation, Environments and the Assistant interface.
